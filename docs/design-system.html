Introduction

This document is the single source of truth for the look and behaviour of this code base. It replaces the separate stijlgids.html, ui-conventies.md and the brand tokens in spec.md: one place where colour, typography, components, patterns, behaviour and accessibility come together.

How to use

Every value here exists as a design token (generated via scripts/build-css.sh) and every component as a Jinja macro in _macros.html. When you build a screen you consult the guide and use the macro — never a loose colour or a hand-styled button. A lint gate (§7) blocks deviations at build time.

Ocean Blue #0051a4 = primary Golden Yellow = accent Indigo = admin shell Radio Canada Big + Inter
Status: proposal v0.1 for approval. The direction is anchored in the existing palette; new or changed decisions are stated explicitly in §6 (Migration) so nothing is dropped silently.

WCAG: text meets at least 4.5:1 contrast (3:1 for ≥18px). The "warmth" comes from the soft ground/surface-2 and whitespace — not from coloured text on coloured surfaces. Semantic colour (success/attention/error) is separate from the accent.
Tokens: --primary --accent --ground --surface --ink --ink-soft --line · macro ui.badge(label, colour)

1.2 Typography

Radio Canada Big for headings (warm, on-brand) · Inter for body and tables. One scale, line height 1.15 for headings, ~1.55 for text.

Tokens: --brand (headings) · --sans (body). Radio Canada Big is embedded; Inter is still to be vendored under /static (§6).
Weight (PROD parity): headings, section titles, card/activity titles and status chips are semibold (600) — airy, not heavy. Extra-bold (700-800) is reserved for the page title, KPI figures and the brand word "Raak". Years (e.g. "2026") are shown in brand blue + a hairline beneath them.

Components

Each pattern built properly once, with a macro name, and identical everywhere. Below, each time: live example + macro + do/don't.

2.1 Buttons

Macros: ui.btn_primary() ui.btn_secondary() ui.btn_fine() ui.btn_danger() ui.btn_icon() — with loading/disabled state.
Do — one filled primary action per screen; the rest calmer.
Don't — outlined buttons everywhere, or "Delete" next to the primary action.

Patterns

The ~13 screens are made of just six real patterns. Build those six well, and every screen is a composition of them.

Admin & public — family, not twins

Both parts share the same tokens, fonts, icons, buttons, form language and notifications — but the expression differs. So everything feels of one house, while each part serves its purpose.

Admin (backend)

  • Calm, efficient, high information density
  • Neutral ground, strong tables & forms
  • Indigo app shell, compact cards, little decoration
  • Fast operation: search, filters, row actions, paging

Public (frontend)

  • More expressive, warmer, more breathing room
  • Larger typography, photos/posters, more Ocean Blue
  • Activity cards, clear calls to action ("Schrijf je in")
  • Fewer tables, more visual hierarchy

Records list — the fixed layout of every records screen

Every admin screen with records (Leden, Activiteiten, Betalingen, Formulieren, Media, Gebruikers, Pagina's) has the same layout in the content column, from top to bottom. So search, "new" and the filters are in the same place everywhere.

  1. Page title
  2. One-line description (optional) — a short subtitle under the title explaining the screen or its access (e.g. "Platformbeheer — enkel OPERATOR")
  3. KPI / management row (optional) — key figures for this screen, e.g. active members, not-yet-renewed, active persons
  4. Primary action — one "+ Nieuwe …" button, styled as the primary (blue) action (not an outline/secondary button); no blue bar around it — the create form opens in a modal or the full-page editor
  5. Search box ("Zoek op …")
  6. Filters — chips (e.g. Komende · Archief · Alles, or a status) and/or a data-driven dropdown (options from the DB, e.g. membership year), like Betalingen — always below "Nieuwe" and the search box, never above
  7. Record cards — clickable; "Bewerken" opens the full-page editor (Screen 4)
No blue bar (HDEV correction): on HDEV every "+ Nieuwe …" button sat in a light-blue tinted block (bg-blue-50) together with a collapsible form. From now on the button stands on its own; the create form opens as a modal (or as a full-page editor), not in a tinted block. And the filters consistently come below "Nieuwe" + search (previously above, e.g. on Media).

Behaviour

"Modern" lives as much in behaviour as in colour. These rules apply everywhere.

✓ Save without unexpected page jumps (htmx)
✓ Visible loading state; button locks after click
✓ Clear notification/toast after saving
✓ Warning on unsaved changes
✓ Filters are preserved after returning/polling
✓ Modals only for short, focused actions
✓ Long details in a side panel instead of a modal
✓ Errors beside the relevant field
✓ Destructive actions never next to the primary action
✓ Visible keyboard focus + correct tab order
✓ Smart default values
✗ Never alert() or confirm()

The GUI is usable by everyone. This is a hard requirement, not an extra.

Governance

Consistency is enforced technically, not hoped for. The chain: tokens → macro → lint gate → this guide.

1 · Tokens (one source). Colour/spacing/type/radii in scripts/build-css.sh (Tailwind standalone, zero Node). Templates refer to them; no loose hex.
2 · Macros. Every component in backend/app/ui/templates/_macros.html. Change a button and it changes everywhere.
3 · Lint gate. A pytest (à la test_i18n_gate) forbids raw colour utilities and loose button classes outside the macros — the build fails on drift.
4 · This guide. A living document; changes here and in the macros go together. Playwright golden screenshots guard the reference screens.
End state: it becomes hard to build an ugly or inconsistent screen — the shortest path is the right path.
